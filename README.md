# ClaimGuard AI - Work Summary

This file records the meaningful changes between the original `draft/` project and the working `main_project/`.

## 1. Frontend UI and UX

### Visual redesign

- Reworked the frontend from the original dark indigo/cyan styling into a warmer enterprise healthcare interface.
- Added a light enterprise theme using:
  - Inter typography
  - deep navy text
  - warm off-white backgrounds
  - white surfaces
  - teal brand accents
  - controlled coral, amber, emerald, and neutral status colors
- Updated the default page theme from dark to light.
- Preserved the existing dashboard, review queue, claim inspector, audit trail, policy/rules, upload, and human-review workflows.

Relevant files:

- `frontend/index.html`
- `frontend/styles.css`
- `frontend/app.js`

### Claim inspection workspace

- Added a Figma-inspired dark Claim Lab inspection mode.
- Added a synthetic claim dossier with provider, service date, payer, coverage, authorization, and line information.
- Added an inspection trace with compact evidence-backed signal cards.
- Added dynamic finding counts and human-review handoff styling.
- Added a workflow strip for:
  1. Ingest
  2. Normalize
  3. Validate
  4. Review
- The final workflow state changes based on the selected claim:
  - `Human handoff` when findings exist
  - `Ready to submit` when the claim is clean
- Failed and unresolved findings can be expanded to show explanations, corrective actions, and evidence paths.

### FHIR payload viewer

- Removed the prediction/check-selection panel from the local inspector.
- Added an inline JSON viewer for the selected claim.
- The viewer generates a FHIR R4-shaped `Claim` resource containing:
  - patient reference
  - provider reference
  - diagnosis
  - insurance/coverage
  - service lines
  - authorization references
  - totals
  - supporting documents
  - synthetic coverage extensions

## 2. Backend Integration

### New API wrapper

Added `backend/src/api.py`, a standard-library HTTP API around the existing backend engine.

Available endpoints:

- `GET /`
- `GET /api`
- `GET /api/health`
- `GET /api/datasets/development`
- `GET /api/datasets/validation`
- `GET /api/datasets/stress`

The dataset endpoints return claims and authoritative deterministic evaluations generated by `backend/src/engine_core.py`.

### Frontend data source

The frontend now loads data from the backend API instead of relying only on `frontend/datasets.js`.

Dataset mapping:

- `worked_cases` -> backend development data limited to 10 claims
- `dev_dataset` -> backend development data
- `val_dataset` -> backend validation data
- `stress_dataset` -> backend stress data

The bundled frontend fixtures remain as an offline fallback when the API is unavailable.

Relevant files:

- `frontend/app.js`
- `frontend/data.js`
- `backend/src/api.py`

### Stress dataset support

- The stress dataset now loads the two added claims as part of the API response.
- The API accepts the existing one-line JSONL records and adjacent pretty-printed JSON objects.
- The frontend selector updates its label from the backend response, showing the actual claim count.
- The stress dataset currently loads as 52 claims.

## 3. Backend and Project Structure

- Kept the deterministic rule engine as the backend source of truth.
- Reused the existing backend implementation for:
  - transport validation
  - rule configuration
  - all 15 deterministic rules
  - evidence generation
  - status calculation
- Kept frontend evaluation only as a fallback for local uploads or offline demo data.
- Preserved the separation between `frontend/` and `backend/`.

## 6. Intentional Scope Limitations

- The API currently provides read-only health and dataset endpoints.
- Review-event persistence, claim-specific API routes, recheck endpoints, and server-side audit endpoints remain future extensions.
- The frontend still supports offline bundled fixtures as a fallback when the backend API is not running.
- The backend data remains synthetic and must not be used as real healthcare or payer data.
